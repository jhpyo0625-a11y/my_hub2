
**Two nodes carry the design's weight.**

`S-05 확인 화면` is the **trust boundary**. Both input paths converge on it, and nothing unstructured reaches the engine without a human approving it. There is no route from OCR or parsing directly into computation.

`ENGINE` is a pure function. Every arrow into it carries approved structured data; every arrow out carries a result and a trace. The LLM appears on this diagram four times and never inside that box.

## 3. Intake journey (S-02 → S-05)

```mermaid
sequenceDiagram
    autonumber
    actor U as 사용자
    participant FE as Frontend
    participant API as FastAPI
    participant OCR as CLOVA OCR
    participant LLM as Claude
    participant DB as SQLite

    U->>FE: 나이 34, 성별 남성
    Note over FE: 성별은 필수 — 성인 구간에<br/>gender=ALL 행이 없음

    U->>FE: 영양제 사진 업로드
    FE->>API: POST /api/intake/ocr
    API->>OCR: image
    OCR-->>API: "산화마그네슘 400mg 1일 1회"
    API->>LLM: raw text + synonyms_ko_label
    LLM-->>API: [{nutrient_code: magnesium,<br/>form: 산화마그네슘, dose: 400, ...}]
    API->>API: validate against nutrients table
    API-->>FE: parsed + unresolved items

    FE->>U: S-05 확인 화면 표시
    Note over U,FE: 매칭 실패 항목은 삭제하지 않고<br/>"확인 필요"로 노출

    U->>FE: 400mg이 원소량인지 화합물량인지 선택
    U->>FE: 승인
    FE->>API: POST /api/reports
    API->>API: ENGINE 계산 (LLM 미개입)
    API->>DB: INSERT report v1
    API-->>FE: report_id + result + trace
```

Steps 6-8 are the only place unstructured text becomes structured data, and step 12 is the only path from there into the engine.

## 4. Report and explanation (S-07 → S-08)

```mermaid
sequenceDiagram
    autonumber
    actor U as 사용자
    participant FE as Frontend
    participant API as FastAPI
    participant LLM as Claude
    participant DB as SQLite

    FE->>U: 리포트 4개 블록
    Note over FE: ① 입력 요약 ② 현재 상태 분석<br/>③ 추천 ④ 참고: 에너지 적정비율

    U->>FE: 마그네슘 "왜 이렇게 나왔나요?"
    FE->>API: POST /api/reports/{id}/chat
    API->>DB: SELECT trace_json WHERE id
    DB-->>API: trace steps
    API->>LLM: trace JSON + 질문<br/>(read-only 지시)
    LLM-->>API: 한국어 설명
    Note over LLM: 새로운 용량 제시 거부<br/>trace에 없는 값 생성 불가
    API-->>FE: 답변

    U->>FE: "멀티비타민을 빠뜨렸어요"
    FE->>U: 입력 수정 버튼 안내
    U->>FE: 입력 수정
    FE->>API: POST /api/reports (parent_id=1)
    API->>API: ENGINE 재계산
    API->>DB: INSERT report v2
    API-->>FE: v2
```

The chat cannot change a recommendation. When the user reveals a missing input, the correct path is 입력 수정 → recompute → v2. Steps 13-17 exist so that the read-only constraint is a workflow, not a dead end.

## 5. Refusal paths (S-90)

```mermaid
flowchart LR

    C1 -->|예| C2{"임신 · 수유 중?"}
    C2 -->|예| R2["S-90<br/>산부인과 상담 권고"]
    C2 -->|아니오| OK["계산 진행"]

    OK --> C3{"영양소별 데이터"}

    C3 -->|"식이 기준 미출처"| U2["UNKNOWN<br/>숫자 미제시"]
    C3 -->|"상한 초과"| OV["OVER<br/>감량 안내 · 최상단"]
    C3 -->|정상| N["DEFICIT / ADEQUATE"]

    OK --> C4{"약물 상호작용"}
    C4 -->|"표에 없는 약물군"| U3["평가되지 않음<br/>약사 상담 안내"]

    style R1 fill:#4a1f1f,stroke:#a33,color:#fff
    style R2 fill:#4a1f1f,stroke:#a33,color:#fff
    style OV fill:#4a3a1f,stroke:#a83,color:#fff
```

Every refusal states its reason. The system declines rather than guesses — a guessed diet baseline systematically over-recommends, and a guessed pregnancy adjustment is worse.

## 6. Report versioning (S-07 ↔ S-09)

```mermaid
stateDiagram-v2
    [*] --> v1 : 최초 계산
    v1 --> v2 : 입력 수정
    v2 --> v3 : 입력 수정
    v1 --> v1 : 채팅 (변경 없음)
    v2 --> v2 : 채팅 (변경 없음)

    note right of v1
        불변. parent_id = null
        profile_json 스냅샷 보관
    end note

    note right of v3
        parent_id = v2
        히스토리에 체인으로 표시
    end note
```

Chat never transitions state. Only 입력 수정 creates a version, and it inserts rather than updates — so any past answer remains explainable by the trace stored beside it.

## 7. Progressive disclosure by phase

The flow above is the Phase 7 end state. Earlier phases short-circuit it:

| Phase | Reachable | Missing |
|---|---|---|
| **2** | S-02 → S-05 (manual only) → S-07 | no OCR, no follow-ups, no chat, no accounts |
| **3** | + S-03 free-text parse | no OCR |
| **4** | + S-04 photo | — |
| **5** | + S-06 follow-ups | — |
| **6** | + S-08 chat | no history |
| **7** | + S-09, S-10 | — |

Phase 2 is a complete user journey with a hand-typed intake. Everything after it removes friction rather than adding capability.
