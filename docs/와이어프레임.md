# 와이어프레임 — UI Wireframes

**Related:** [화면흐름도.md](화면흐름도.md) · [기능명세서.md](기능명세서.md) · [api.md](api.md)

Five screens as working HTML. Open [`wireframes/index.html`](wireframes/index.html) in a browser and click through — the top navigation links every screen.

```
docs/wireframes/
  index.html        screen index, entry point
  wireframes.css    shared stylesheet, no external assets
  intake.html       S-02 기본 정보 입력
  confirm.html      S-05 확인 화면
  report.html       S-07 리포트
  chat.html         S-08 근거 채팅
  history.html      S-09 히스토리
```

Static mockups — no computation, no network. Every number shown is a **verified example from the spec** (magnesium, M 34, 산화마그네슘 600mg), not invented filler, so the layout is stress-tested against real values rather than tidy ones.

---

## Design constraints

These come from the product, not from taste. Each one is visible in the markup.

| Constraint | How it shows up |
|---|---|
| Sex cannot be defaulted | Marked required with the reason inline: 철 여성 12mg vs 남성 8mg |
| Weight affects nothing | Stated on the field *and* again in the report. Never implied to matter |
| Nothing computes before a human confirms | S-05 blocks submit while any 확인 필요 row remains |
| Over-supplementation leads | `OVER` renders first, in amber, as a reduction instruction — not a dose |
| Every number is traceable | Each nutrient carries a `<details>` trace with the rules that fired |
| AMDR is reference, not assessment | Block ④ has no trace, and says why |
| The chat cannot issue a dose | Refusals route to 입력 수정 rather than dead-ending |

## S-02 — 기본 정보 입력

[`wireframes/intake.html`](wireframes/intake.html)

Four groups: 기본 정보 (age, sex, weight, goal) · 임신·수유 · 복용 중인 약 · 검진 수치.

**Required fields carry their reason, not just an asterisk.** Sex is the only field that cannot fall back to a national default, and the form says exactly why:

```html
<div class="field">
  <label>성별 <span class="req">*</span></label>
  <div class="seg">
    <button type="button" aria-pressed="true">남성</button>
    <button type="button" aria-pressed="false">여성</button>
  </div>
  <p class="why"><strong>건너뛸 수 없는 항목입니다.</strong>
    2025 섭취기준에는 성인 구간에 성별 공통 기준이 없습니다.
    예를 들어 철은 여성 12mg, 남성 8mg으로 기준 자체가 다릅니다.</p>
</div>
```

Weight gets the opposite treatment — collected, but the helper text says it does not affect the result. Silently storing a field the user believes is being used would be the worse choice.

Biomarkers carry an inline notice that they change **priority only**, never the target.

## S-05 — 확인 화면 · trust boundary

[`wireframes/confirm.html`](wireframes/confirm.html)

The single most important screen. Both OCR and manual entry land here, and nothing reaches the engine without passing through it.

**Unresolved rows are shown, never dropped.** A silently discarded item is invisible to the user:

```html
<tr class="needs-check">
  <td><strong>—</strong> <span class="tag">확인 필요</span></td>
  <td colspan="4" style="color:var(--danger)">
    라벨에서 <code>“이뮨플러스 컴플렉스”</code>를 읽었지만 영양소를 특정하지 못했습니다.
    직접 선택해 주세요.
  </td>
  <td><button class="btn btn-ghost btn-sm">선택</button></td>
</tr>
```

Submit stays disabled while any such row exists — the API rejects it as `UNRESOLVED_INTAKE` regardless, so the UI simply agrees with the contract.

**Ambiguous labels get an explicit choice.** "마그네슘 600mg" is either the compound or the element, and the two differ by ~2.5×. The screen asks rather than assumes, and shows both resulting numbers so the choice is informed.

A summary strip closes the screen, including the folate case where one tablet produces two numbers — 340 µg DFE toward the target, 200 µg toward the limit.

## S-07 — 리포트

[`wireframes/report.html`](wireframes/report.html)

Four blocks, matching [api.md](api.md) response shape exactly.

| Block | Content |
|---|---|
| ① 입력 요약 | Parsed profile + 입력 수정 button |
| ② 현재 상태 분석 | Per-nutrient status, four figures, expandable trace |
| ③ 추천 | Amount, form + reason, timing, interaction flags |
| ④ 참고 | AMDR ranges, explicitly not evaluated |

**Four statuses, four visual treatments.** The mockup renders one of each so the styling is proven against all of them: `OVER` (마그네슘), `DEFICIT` with a biomarker flag (철), `ADEQUATE` (엽산), `UNKNOWN` (크롬).

`OVER` gets a tinted card border and leads the block:

```html
<div class="nutrient is-over">
  <div class="nutrient-head">
    <span class="name">마그네슘</span>
    <span class="pill over">상한 초과</span>
  </div>
  <div class="callout">
    현재 보충제 섭취량이 상한섭취량을 <strong>11.8mg 초과</strong>합니다. 용량을 줄이세요.
  </div>
  <dl class="numbers">
    <div><dt>목표 섭취량</dt><dd>380<small>mg</small></dd></div>
    <div><dt>식품 기여</dt><dd>266<small>mg</small></dd></div>
    <div><dt>보충제 기여</dt><dd>361.8<small>mg</small></dd></div>
    <div class="neg"><dt>상한 여유</dt><dd>−11.8<small>mg</small></dd></div>
  </dl>
</div>
```

The negative headroom is rendered as a number, not hidden — it *is* the excess.

**Traces are collapsed by default, one per nutrient**, and each step shows the rule, the arithmetic, and the citation:

```html
<details class="trace">
  <summary>이 숫자는 어떻게 나왔나요?</summary>
  <div class="trace-body">
    <div class="trace-step">
      <span class="rule">intake.accumulated</span> ·
      <span class="calc">산화마그네슘 600mg × 60.3% × 1회 = 361.8 mg</span><br>
      <span class="cite">MgO 분자량 40.30 / 24.31</span>
    </div>
    <div class="trace-step">
      <span class="rule">limit.resolved</span> ·
      <span class="calc">350 mg · 보충제 기준(supplemental_only) → 식품 기여 제외</span><br>
      <span class="cite">KDRI 2025 마그네슘 상한섭취량 — 식품 외 급원에만 적용</span>
    </div>
  </div>
</details>
```

`UNKNOWN` shows the target and current intake but renders `—` for the recommendation, with the reason stated: no sourced diet baseline means a computed number would over-recommend.

**Block ④ deliberately has no trace.** Nothing was computed, and the block says so — the asymmetry against blocks ② and ③ is the point.

## S-08 — 근거 채팅

[`wireframes/chat.html`](wireframes/chat.html)

The mockup scripts the two conversations that define the feature's boundary.

**Refusing to issue a dose:** the user asks for a 500mg recommendation. The reply explains that the chat explains stored calculations and does not produce doses, then hands over a 입력 수정 button. The read-only constraint is a workflow, not a dead end.

**Handling a forgotten input:** the user mentions an unlogged multivitamin. Rather than adjusting numbers in conversation, the reply notes the effect direction and routes to 입력 수정.

Every answer cites the trace line it came from. The version binding is stated at the top: this conversation belongs to v1 and stays there.

## S-09 — 히스토리

[`wireframes/history.html`](wireframes/history.html)

Revision chains as a vertical timeline, newest first, with what changed between versions:

```html
<div class="chain-item current">
  <div class="ver">v3 <span class="pill adequate">현재</span></div>
  <div class="meta">8월 10일 15:42 · 멀티비타민 추가 · 상한 초과 0 · 부족 9</div>
</div>
```

The v1 → v3 progression shows the product working: initial `OVER`, form changed, missing supplement added, warning resolved. Old versions keep their numbers even after guidelines are revised, because each stores its own snapshot and trace.

## Responsive and accessibility notes

- Single column at ≤ 640px; the four-figure `numbers` grid collapses to 2×2.
- All interactive controls are real `<button>`, `<input>`, `<select>` elements — no `<div>` handlers.
- Status is conveyed by **label text plus color**, never color alone. `상한 초과` reads correctly in greyscale.
- `<details>`/`<summary>` for traces gives keyboard and screen-reader support with no JavaScript.
- Numeric columns use `font-variant-numeric: tabular-nums` so figures align across rows.
- Korean-first font stack (Pretendard → Apple SD Gothic Neo → Malgun Gothic) with system fallbacks. No web fonts, so the files open offline.
